# Промпт для аудита и регулярной проверки качества

Проанализируй и доработай anime-news-bot: надёжность развёртывания, качество
постов (текст, фото, видео), интерес новостей, модерация, экономия ресурсов.
Работай от актуальной main в отдельной ветке, сохраняя пользовательские
изменения.

## Сначала — факты о хостинге (Bothost, документация: bothost.ru/llms-full.txt)

- Образ собирается автоматически: `COPY requirements.txt` →
  `pip install --no-cache-dir -r requirements.txt` → код. `requirements.txt`
  обязан быть самодостаточным: никаких `-c`/`-r` на соседние файлы (из-за
  `-c constraints.txt` однажды не деплоилась ни одна версия).
- Python берётся из образа хостинга и может не совпадать с `runtime.txt`
  (бывал 3.10). Код и версии пакетов должны работать на 3.10–3.13.
- В образе нет ffmpeg, deno и прочего системного: всё нужное — только pip
  (`imageio-ffmpeg`, `yt-dlp[default,deno]`).
- `/app` монтируется с кодом из Git, `/app/data` — постоянный том (`DATA_DIR`).
- Память: бесплатный тариф 256 МБ, базовый 1 ГБ, Pro 2 ГБ. Вылет по памяти —
  «Killed», код 137, без traceback.
- Автообновление по push — только на платных тарифах; иначе «Обновить из Git».
  Ошибки установки — в «Логах сборки», падения бота — в «Логах работы».
- CI повторяет сборку хостинга: задача `hosting-image` (чистые
  `python:3.11-slim` и `python:3.10-slim`, `tools/hosting_smoke.py`: тяжёлые
  модули делают настоящую работу, бот доходит до опроса Telegram на пустом
  томе данных).

## Порядок работы

1. Прочитай инструкции репозитория и проверь состояние Git. Уточни реальные
   симптомы по доступным логам, не выводя токены, ключи и содержимое .env.
   Владельца можно попросить строки лога (без токенов), но не `/backup`.
2. Если бот не запускается — сначала деплой: соберись «как хостинг» (только
   requirements.txt в пустой папке, затем `tools/hosting_smoke.py`), проверь
   3.10 и 3.11.
3. Качество постов сверяй с живым каналом: `t.me/s/<канал>` отдаёт посты с
   подписями авторов (бот против админов), реакциями и картинками (до 800 px).
   Реальный текст канала и чата в репозиторий не попадает: в тестах —
   пересказанные примеры, в отчётах — пересказ.
4. Проверь LLM: выбор профиля, квоты запросов и токенов, 429/5xx, таймауты,
   JSON, кеш. Новость должна опираться на источник; модель не дописывает
   факты из памяти. Модели новостей и модерации независимы.
5. Модерация: никаких автоматических банов — бан только кнопкой админа 🚫;
   муты и предупреждения бот выдаёт сам.
6. Исправляй воспроизводимые ошибки небольшими изменениями. На каждую ошибку —
   регрессионный тест, который падает до исправления; каждый новый тест
   ловит мутацию (прогон мутаций с таймаутом, исходники после него сверить).
7. Выполни затронутые тесты, затем CI целиком один раз: pyflakes, ruff F821,
   pytest (BOT_TOKEN, DATA_DIR) на 3.10 и 3.11, `tools/build_manifest.py
   --check` (после `git add -A`), `tools/check_invariants.py`,
   `tools/env_reference.py --check`.
8. Отчёт владельцу по-русски и просто: причина → исправление → проверка →
   что сделать в панели. Различай локальное исправление, PR и обновление
   запущенного бота.

Только бесплатные инструменты и сервисы. Комментарии в коде — по-русски и
объясняют «почему». Экономь лимиты: ограничивай область поиска и вывод
инструментов, делегируй только независимые короткие задачи.


## Регулярная проверка качества постов (раз в 1–2 недели)

Качество постов — главное, что видят подписчики, и оно портится тихо:
модель меняется, источники меняют формат, новые случаи обходят фильтры.

1. **Собрать живые данные.** Страница `t.me/s/<канал>?before=N` — посты за две
   недели с подписью автора (бот или админ) и текстом. Данные — только во
   временную папку, в репозиторий не коммитить; в тестах — пересказанные примеры.
2. **Текст каждого поста бота** проверить по списку:
   - название тайтла: официальное русское (Shikimori) или латиница источника;
     одно имя на тайтл во всех постах; нет ромадзи при известном русском.
     Если ромадзи пошли пачкой — это не модель, а Shikimori: строка
     «Shikimori (названия тайтлов)» в `/health` покажет сбои подряд и
     последнюю ошибку; пост в таком случае ждёт ответа до 4 циклов сбора
     (`_title_lookup_failed`, `_title_defer_news`);
   - вторая строка не пересказывает заголовок; нет пустых фраз («дата не
     указана», «подробности позже»); нет обрывков и пропавших слов;
   - грамматика: род и число («Анонсировано кроссовер» — ошибка), падежи после
     предлогов, кавычки-ёлочки у кириллицы;
   - нет жаргона (KV, PV, тизер-постер, визуал, «Выдали», Manga/spin-off/light
     novel латиницей), капса, ссылок, чужих хэштегов, подписей источника,
     иероглифов, двойных кавычек ««…»», знаков ударения;
   - строка «о чём» (цитата) — только у аниме и манги, не пересказывает текст
     выше и не называет другой тайтл; проверить долю общих слов на выборке
     (`_about_repeats`, порог `ABOUT_ECHO_SHARE`);
   - заголовок говорит, ЧТО случилось и с КАКИМ тайтлом; эмодзи по смыслу;
     посты без эмодзи — правленные админом: посмотреть, что именно он стёр
     (так нашлись значок 🔄 и пометка «Обновление:», которые админы убирали
     руками);
   - нет спойлеров, юбилеев, дней рождения, выхода серий (их бот не публикует),
     западного кино больше одного поста в сутки.
3. **Дубли.** Найти пары постов об одном событии одного тайтла за 36 ч — бот с
   ботом и бот с админом — и для каждой выяснить, почему дедуп промахнулся:
   прогнать оба заголовка через `_work_identity_keys`, `story_event_classes`,
   `has_similar_title`, дедуп картинок. Частая причина — латинское и русское
   имя одного тайтла без общего ключа: проверить, знает ли их пару
   `WorkAliases` (`work_aliases.json`). Посмотреть на разницу во времени:
   повтор ровно через 24 или 36 часов после первого поста — это пост, который
   ждал в ветке конца окна (`WorkMemory.seen`, окна считаются от попадания
   поста в ветку). Пост с отметкой обновления сюжета обходит сравнение
   заголовков — проверить, что нового в нём действительно есть
   (`classify_update`: номер, дата, род события; «в апреле» и «апрель 2027» —
   одна дата).
4. **Каждую находку** — до причины в коде, затем регрессионный тест на
   пересказанном примере, затем исправление. Без причины не чинить.
5. **Отчёт владельцу:** что нашли (с примерами), что исправлено, что осталось.

## Чек-лист полного аудита

Агентов — 3–5, у каждого своя непересекающаяся область, все только читают:
качество текста по живому каналу; дубли по живому каналу; баги надёжности
(публикация, отложка, ветка, модель, рестарты); безопасность и
производительность (память контейнера, токены модели, диск, зависимости).
Находки агентов — гипотезы: каждую проверить самому по коду и коротким
запуском, ложные отбросить, подтверждённые исправить небольшими
изменениями с тестами. Перед push — все проверки из «Порядка работы», коды
завершения смотреть напрямую, а не через `| tail`.
